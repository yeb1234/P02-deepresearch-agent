这轮说明两件事：1/1 能跑通，且成本明显下降；但少一次检索后，覆盖度和引用质量都掉了一档（4.6 → 4.0），属于预期内的取舍，不是回归。

## 解读

1. **分数只能作方向性参考，不能当作绝对排名。** 两份报告由不同 Judge 评分，DeepSeek 报告拿到的 Qwen Judge 明显更宽松；Qwen 报告拿到的 DeepSeek Judge 对引用格式更严格。4.6 与 4.8 的差距小于 Judge 口径差异。
2. **DeepSeek V4.1-Flash 更偏“证据型写作”。** 报告长度约为 Qwen 的 2.2 倍，引用 30 条，正文里做了 A/B/C 级信源分级；事实准确性与引用质量都是 5/5。代价是生成慢、输出长，且内部 critic 给分反而更低（5.5 → 6.5），说明它对自己的稿子更苛刻。
3. **Qwen3.8-Flash 更偏“快速成稿”。** 4 分 20 秒生成 8,509 字符，结构完整、覆盖度高，适合先出可用初稿；但事实准确性 4/5、引用质量 4/5，Judge 指出部分引用标注的显示形式不够统一。
4. **内部审稿不能替代外部评估。** Qwen 的内部 critic 从 7.0 提到 8.5，但外部 DeepSeek Judge 只给 4.6；DeepSeek 的内部 critic 只给 6.5，外部 Qwen Judge 却给 4.8。两套口径差异明显，后续评估应保留外部 Judge，并尽量固定同一 Judge 做纵向对比。
5. **两份报告都没有触发幻觉判定。** 这是低难度、单主题、短链路的结果，不能外推到高难度长报告。

## 成本与性能

- 主对比两轮各约 4.5 分钟，各发生 2 个查询、2 轮检索、1 次初稿修订、1 次润色、1 次 Judge 调用。
- 主链路模型确实走了低成本 Flash 档；两轮主对比跑在事实抽取修复前，`FactExtractor` 仍是 `deepseek-v4-pro`，各调用 4 次左右。修复后的 1/1 验证已显式切到 `deepseek-v4.1-flash`。
- KB embedding 走 `text-embedding-v3`，MCP 搜索本身也有调用成本；Judge 各调用 1 次，成本相对小。
- 因此主对比适合判断“Flash 档能不能出可用报告”，不适合拿来做精确成本核算；1/1 验证适合看最低成本下限。

## 发现

### 1. 评估器同步/异步不匹配（已修）

`backend/eval/evaluator.py` 原来用 `graph.invoke` 调图，但主图节点是 async，第一次运行直接报：

```text
No synchronous function provided to "generate_plan".
```

已改为 `asyncio.run(graph.ainvoke(...))` 的同步桥接，Qwen 与 DeepSeek 两轮均通过。

### 2. 评估代码不在 backend 镜像里（已修）

`backend/Dockerfile` 原来只 `COPY src` 和 `scripts`，没有 `eval`。当时用 `docker cp backend/eval/. <container>:/app/eval` 临时注入才跑起来。

已修：Dockerfile 增加 `COPY eval ./eval`；2026-11-17 重建 backend 镜像，并直接在新镜像里跑通 1 查询 / 1 循环评估，`eval` 与 `run_eval.py` 都已在镜像内。

### 3. CLI 的查询数/循环数被 `.env` 覆盖（已修）

`Configuration.from_runnable_config()` 优先读环境变量，再读 `configurable`。容器里已有：

```text
NUMBER_OF_INITIAL_QUERIES=2
MAX_RESEARCH_LOOPS=2
```

所以 `--initial-queries 1 --max-loops 1` 没有生效，实际跑了 2 个查询、2 轮检索。两轮结果都是修复前跑的 2/2，保留作为基线。

已修：`run_eval.py` 现在在调用 `Evaluator` 前把 CLI 值写回 `NUMBER_OF_INITIAL_QUERIES` / `MAX_RESEARCH_LOOPS`，因此 CLI 会覆盖 `.env`。直接调用 `Evaluator` 而不经过 CLI 时，仍需自己设这两个环境变量。

### 4. 事实抽取模型没有走低成本档（已修）

`backend/src/agent/kb/extractor.py` 原来把 `FactExtractor.__init__(model_id="deepseek-v4-pro")` 写死。主链路已经切到 Flash，但 KB 事实抽取仍是 Pro。

已修：`FactExtractor` 现在优先用显式 `model_id`，否则读 `KB_EXTRACTOR_MODEL`，最后回退 `deepseek-v4-pro`；默认行为不变，低成本评估可以显式设 `KB_EXTRACTOR_MODEL=deepseek-v4.1-flash`。`.env.example` 与 README 已补该变量。

### 5. JSON 解析重试

DeepSeek 这轮的 critic review 有一次 `JSONDecodeError`，触发 1 次重试后成功。说明 critic 输出的 JSON 仍可能被截断或转义错误；当前重试机制兜住了，但会增加耗时。

## 建议下一步

1. 固定同一个 Judge（建议 DeepSeek V4.1-Flash）做 Qwen / DeepSeek 的纵向对比，减少 Judge 口径差异。
2. 用同一 Judge 再跑 2/2 与 1/1，量化“多一轮检索”对覆盖度和引用质量的实际增益。
3. 只有在预算明确时才跑完整 10 条测试集；当前单条低难度用例已经能暴露执行器与成本路由问题。
4. 修 critic 的 JSON 解析路径（截断、未转义引号），减少重试带来的额外耗时。
