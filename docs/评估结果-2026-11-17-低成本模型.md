# 低成本模型端到端评估（2026-11-17）

## 测试设置

| 项 | 值 |
|---|---|
| 用例 | `backend/eval/test_set.json` 第 5 条，难度 `low`：规范驱动开发（SDD）与 AGENTS.md 的关系及最佳实践 |
| 模式 | `--mode e2e`，端到端生成报告 + 5 维评分 |
| 预期参数 | 1 个初始查询、1 次研究循环 |
| 实际参数 | 2 个初始查询、2 轮检索（被 `.env` 的 `NUMBER_OF_INITIAL_QUERIES=2`、`MAX_RESEARCH_LOOPS=2` 覆盖，见“发现”） |
| 运行环境 | Docker backend 容器，Milvus KB 开启，Redis 搜索缓存开启 |
| 交叉评分 | Qwen3.8-Flash 生成的报告由 DeepSeek V4.1-Flash 评；DeepSeek V4.1-Flash 生成的报告由 Qwen3.8-Flash 评 |

## 结果

| 指标 | Qwen3.8-Flash | DeepSeek V4.1-Flash |
|---|---|---|
| 总评分 | **4.6 / 5** | **4.8 / 5** |
| 事实准确性 | 4 / 5 | 5 / 5 |
| 信息覆盖度 | 5 / 5 | 4 / 5 |
| 逻辑结构 | 5 / 5 | 5 / 5 |
| 时效性 | 5 / 5 | 5 / 5 |
| 引用质量 | 4 / 5 | 5 / 5 |
| 幻觉 | 无 | 无 |
| 报告长度 | 8,509 字符 / 126 行 / 5 个二级标题 | 18,897 字符 / 254 行 / 6 个二级标题 |
| 捕获来源条目 | 90 | 94 |
| 正文引用数 | 26 | 30 |
| 内部审稿 | 7.0 → 8.5，1 次修订 | 5.5 → 6.5，1 次修订 |
| 运行耗时 | 约 4 分 20 秒 | 约 4 分 37 秒 |
| Judge 模型 | DeepSeek V4.1-Flash | Qwen3.8-Flash |

## 解读

1. **分数只能作方向性参考，不能当作绝对排名。** 两份报告由不同 Judge 评分，DeepSeek 报告拿到的 Qwen Judge 明显更宽松；Qwen 报告拿到的 DeepSeek Judge 对引用格式更严格。4.6 与 4.8 的差距小于 Judge 口径差异。
2. **DeepSeek V4.1-Flash 更偏“证据型写作”。** 报告长度约为 Qwen 的 2.2 倍，引用 30 条，正文里做了 A/B/C 级信源分级；事实准确性与引用质量都是 5/5。代价是生成慢、输出长，且内部 critic 给分反而更低（5.5 → 6.5），说明它对自己的稿子更苛刻。
3. **Qwen3.8-Flash 更偏“快速成稿”。** 4 分 20 秒生成 8,509 字符，结构完整、覆盖度高，适合先出可用初稿；但事实准确性 4/5、引用质量 4/5，Judge 指出部分引用标注的显示形式不够统一。
4. **内部审稿不能替代外部评估。** Qwen 的内部 critic 从 7.0 提到 8.5，但外部 DeepSeek Judge 只给 4.6；DeepSeek 的内部 critic 只给 6.5，外部 Qwen Judge 却给 4.8。两套口径差异明显，后续评估应保留外部 Judge，并尽量固定同一 Judge 做纵向对比。
5. **两份报告都没有触发幻觉判定。** 这是低难度、单主题、短链路的结果，不能外推到高难度长报告。

## 成本与性能

- 两次运行各约 4.5 分钟，各发生 2 个查询、2 轮检索、1 次初稿修订、1 次润色、1 次 Judge 调用。
- 主链路模型确实走了低成本 Flash 档；但**并非完全低成本**：
  - `FactExtractor` 的默认模型仍是硬编码的 `deepseek-v4-pro`，两轮各调用 4 次左右做事实抽取。
  - KB embedding 走 `text-embedding-v3`，MCP 搜索本身也有调用成本。
  - Judge 各调用 1 次，成本相对小。
- 因此这轮适合判断“Flash 档能不能出可用报告”，不适合拿来做精确成本核算。

## 发现

### 1. 评估器同步/异步不匹配（已修）

`backend/eval/evaluator.py` 原来用 `graph.invoke` 调图，但主图节点是 async，第一次运行直接报：

```text
No synchronous function provided to "generate_plan".
```

已改为 `asyncio.run(graph.ainvoke(...))` 的同步桥接，Qwen 与 DeepSeek 两轮均通过。

### 2. 评估代码不在 backend 镜像里

`backend/Dockerfile` 只 `COPY src` 和 `scripts`，没有 `eval`。当前用 `docker cp backend/eval/. <container>:/app/eval` 临时注入才跑起来。要长期可复现，应在 Dockerfile 增加 `COPY eval ./eval`。

### 3. CLI 的查询数/循环数被 `.env` 覆盖

`Configuration.from_runnable_config()` 优先读环境变量，再读 `configurable`。容器里已有：

```text
NUMBER_OF_INITIAL_QUERIES=2
MAX_RESEARCH_LOOPS=2
```

所以 `--initial-queries 1 --max-loops 1` 没有生效，实际跑了 2 个查询、2 轮检索。要真正压到 1/1，需要在 `docker exec` 时显式传：

```bash
-e NUMBER_OF_INITIAL_QUERIES=1 -e MAX_RESEARCH_LOOPS=1
```

### 4. 事实抽取模型没有走低成本档

`backend/src/agent/kb/extractor.py` 的 `FactExtractor.__init__(model_id="deepseek-v4-pro")` 是硬编码默认值。主链路已经切到 Flash，但 KB 事实抽取仍是 Pro。若要把低成本评估做干净，建议增加 `KB_EXTRACTOR_MODEL` 环境变量，默认保持 `deepseek-v4-pro` 不变。

### 5. JSON 解析重试

DeepSeek 这轮的 critic review 有一次 `JSONDecodeError`，触发 1 次重试后成功。说明 critic 输出的 JSON 仍可能被截断或转义错误；当前重试机制兜住了，但会增加耗时。

## 建议下一步

1. 用 `NUMBER_OF_INITIAL_QUERIES=1`、`MAX_RESEARCH_LOOPS=1` 再跑一次单模型，确认真实最小成本与耗时。
2. 固定同一个 Judge（建议 DeepSeek V4.1-Flash）做 Qwen / DeepSeek 的纵向对比，减少 Judge 口径差异。
3. 给 `FactExtractor` 增加 `KB_EXTRACTOR_MODEL`，让“低成本档”名副其实。
4. 在 Dockerfile 中加入 `COPY eval ./eval`，或把 `backend/eval` 作为 volume 挂载，避免每次 `docker cp`。
5. 只有在预算明确时才跑完整 10 条测试集；当前单条低难度用例已经能暴露执行器与成本路由问题。
